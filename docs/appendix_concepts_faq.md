## 1. CAP 定理与 PACELC 模型

- **CAP 定理 (Brewer)**：在网络分区 (Partition Tolerance, P) 必然存在的分布式物理环境中，系统只能在**强一致性 (Consistency, C)** 与**高可用性 (Availability, A)** 之间做出权衡。
- **PACELC 模型 (Abadi)**：在没有网络分区 (Else, E) 的常规状态下，系统仍然必须在**延迟 (Latency, L)** 与**一致性 (Consistency, C)** 之间权衡。

## 2. 经典主备复制与共识协议对比

| 属性 | 主备复制 (VMware FT) | Raft 共识协议 | Paxos 协议族 |
| :--- | :--- | :--- | :--- |
| **复制层级** | 硬件指令、CPU 寄存器、DMA 内存 | 应用状态机日志条目 | 状态机提案 (Proposals) |
| **节点数量** | 2 节点 (主 + 备) | 通常 3 或 5 节点 | 通常 3 或 5 节点 |
| **容错数量** | 容忍 1 个故障 (通过共享存储仲裁) | $2f+1$ 节点容忍 $f$ 个故障 | $2f+1$ 节点容忍 $f$ 个故障 |
| **脑裂防范** | 共享存储硬件级原子锁 (Test-and-Set) | 多数派选举法定人数 (Quorum) | 多数派选举法定人数 (Quorum) |
| **多核支持** | 极难 (单核限定) | 天然支持并发多核业务 | 天然支持并发多核业务 |
| **客户端延迟** | 受限于 Output Rule 与 ACK 往返 | 受限于 Leader 广播与多数派写入 | 受限于两轮或单轮多数派 RPC |

## 3. 分布式系统经典面试必问 Q&A

??? question "Q1: 为什么 Raft 需要多数派（Majority）而不是仅仅一半（Half）？"
    **答案**：因为任意两个多数派集合必然至少存在一个公共重叠节点（Pigeonhole Principle，抽屉原理）。这保证了新当选的 Leader 所在的大多数集合中，必定至少包含一个拥有最新已提交日志的节点，从而确保已提交日志绝不丢失。

??? question "Q2: 什么是拜占庭故障？为什么 Raft/Paxos 不能防止拜占庭故障？"
    **答案**：拜占庭故障指的是节点可能发送虚假、伪造、篡改或相互矛盾的消息。Raft 和 Paxos 均构建在 Fail-Stop（非拜占庭）模型下，完全信任 Leader 发来的任期与日志真实性。如果 Leader 发生拜占庭叛变并伪造数据，Raft 集群将直接接受错误状态。防御拜占庭故障必须采用 PBFT 等具备数字签名交叉校验的算法，且需要至少 $3f+1$ 个物理节点。
